# 队列和派活

你是编排者：分派、核对、发起审查、排合并顺序。业务代码交给执行方（子 agent 或外部 agent）。日常推进用 `/next`（`skills/next/SKILL.md`）；本模块讲队列格式、怎么派、怎么接力。

## 1. 队列

`docs/queue.md`，只由编排会话写。一行一项：

```
| # | 目标 | 完成标准 | 档 | 依赖 | 状态 |
```

- 每格短：目标一句，完成标准写要保证的行为和怎么证明，细节放计划文件或提交正文，格里只留指针。内容里的 `|` 写成 `\|`。
- 状态只有：待做 / 在做 / 待用户 / 待放行 / 完成 / 搁置，后面用括号写一句说明。"在做"写 `在做（<日期 时间> 起）`；接力写 `待做（接力：<做到哪、下一步>；分支 <分支>）`。
- 表格上方只留当前有效的一段说明（顺序、授权）；过时的移进 `docs/decision-log.md`。
- 完成的只留最近 5 行；搁置的移到 `docs/queue-shelved.md`（表头一样，开工不读，要恢复或查依赖时搜）。状态脚本两份一起读。
- 新想法、审查报的现实 P2、主干原来就红的测试都进队列；加之前先在两份文件里搜同样字样。
- 有远程、项目用 issues 的，按项目。

## 2. 派活

- 用后台子 agent 加 worktree 隔离，或经 `dispatch.ps1`、宿主的派活工具交给外部 agent（具体写法见 `hosts.md`）。每项一个 worktree。
- 并行上限按信任等级（总览第 4 节），项目 `AGENTS.md` 可以定得更小。会改同一批核心文件的不并行；用独占资源（宿主软件、设备）的排进慢验证队列。
- **一次只交一件能独立验证、单独提交的事**。大改写先拆成几步，每步有完成标准。
- 派活说明自包含，写清：
  - 目标、先读哪些文件、完成标准；
  - 边界情况和口径：你先想一遍写进完成标准，不留给执行方猜，也不写实现提示。只写正常使用会碰到的情况；高风险的（派活和合并关口、隔离、鉴权、数据迁移、写入器）另附一份**要拦住的反例清单**，每条写具体输入和应有结果（路径大小写和 `..`、符号链接和 junction、空值和空环境变量、参数缩写、换个入口绕过）；
  - 不加没人要的功能：用户写错能直接报错的，不做自动推断；
  - 改了别的代码在用的参数或格式：搜出全部调用方，跑它们的测试；
  - 按 `build.md` 证明；边界（不 push、不合并、不改队列、方向性选择不自己定）；
  - 每条写下的事实先用命令确认，确认不了写"未查到"；临时文件放系统临时目录，结束时只留已提交的改动；
  - 结束回复只写三行（结果 / 跑了 / 风险），加提交正文草稿。
- 队列、计划、`LESSONS.md` 只由你维护，执行方把要同步的写进回复。
- **派出去的活还在跑，就不结束回合**：等它的完成通知，手上没事就前台等。
- **按难度分工**：机械活（批量回归、补用例、按明确规则整理）给便宜的；要核对事实、做判断、改核心代码的给强的。一项只派一个审查方审全部改动。
- **你怎么核对**：不读完整 diff，看三样：执行方的三行回复、审查方跑的测试（命令、退出码、head）、审查结论。对不上或结论是 Fix 再看 diff。

## 3. 模型设置表

谁写、谁审、谁编排只记在总览 `<总览>/models.json` 一处（格式见 `templates/models.example.json`）：每个角色一列有序候选（provider、model、强度），`disabled` 写停用到哪天。

- 派前查：`pwsh -NoProfile -File <skill>/scripts/models.ps1 -Role <角色> -Config <总览>/projects.json [-Writer <写方模型>] [-Json]`。审查带 `-Writer`，脚本跳过同厂商的候选。退出 3 是候选全被跳过，告诉用户，不自己挑；退出 2 是表写错了。
- 角色：`orchestrate`、`build-backend`、`build-frontend`、`mechanical`、`review`、`review-high-risk`。
- 用户说"后端全给某个模型""某个模型停到周五"这类，只改表里那一行，在总览 `decisions.md` 记一条。看不到总览的会话写进总览的 `docs/requests.md`。
- 某家额度用完、表里候选派不出去时，按表里的下一个，不靠记忆换。

## 4. 接力

执行方完成后：核对（回复是自述，亲自看 head 和产物）→ 发起审查（`verify.md`）→ 要修的交回原执行方（续上它的上下文，或在同一分支再派）→ 合并（`land.md`）→ 更新队列 → 三行汇报 → 有空位就补下一项。

## 5. 关联项目

一个项目用另一个项目的产出时，各开各的会话，靠接口约定连起来：

- 新接口或不兼容改动，提供方先写合同（格式、版本、拒绝什么、错误怎么报），使用方复核后各自做。使用方给的最小复现和正例做成提供方快检里的用例。
- 提供方合并后发带版本的冻结包（文件清单加散列）；使用方锁版本，升级是自己队列里的一项。
- 需求单向流动：使用方写进提供方的 `docs/requests.md`（附最小复现），再叫醒对方会话（`portfolio.md` 第 3 节）。不在使用方会话里改提供方的代码。
- 提供方优先做卡住使用方北极星的项。
