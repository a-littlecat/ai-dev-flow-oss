# 做：理解 → 做 → 证明

每个改动由一个执行方在自己的 worktree 里做完，交独立审查（`verify.md`），再合并（`land.md`）。

## 1. 理解

- 先读 `AGENTS.md`、相关子系统文档、`LESSONS.md`，项目有 `docs/code-standards.md` 的也读。读完整的来源：整段对话、issue 全部评论；用户说过"先别做"的照办。
- 能查清的不问。会改变范围或后果的按总览第 3 节问；其余模糊点写成默认假设往下做，写进提交正文。
- 碰到方向性选择，先照 `direction.md`。
- 只在两种情况写计划 `docs/plans/<主题>.md`：跨几天、要拆成多项；单向门要先给用户看方案。计划只写目标与非目标、方案和取舍、拆成哪几项、每项怎么证明、要用户拍板的点。

## 2. 做

- 一个改动一个 worktree 和分支；只改文档的可以直接在主干上做。
- 只做目标需要的部分，不留 TODO，不交半成品。
- 修 bug 修到所有同类位置：grep 同样的写法一起改。
- 契约变了（接口、文件格式、行为），同一个改动里更新文档。
- 改了别的代码在用的参数或格式，搜出全部调用方，跑它们的测试。
- 同一句提醒要写第二遍时，改成测试、lint 或断言。

## 3. 证明

- **在真实产物上验证**：跑 verify；用户看得到的行为实际操作一遍。"能编译"不是证据。
- **少加测试，多跑真实数据**：新测试只要最关键的一两条，每条改坏会红。改了的功能拿项目里真实的输入只读跑一次（真实队列、真实图纸的副本、线上数据的只读查询），命令和结果摘要写进提交正文；没有真实数据的写"真实数据：没有，<原因>"。
- **亲手改坏**：撤掉修复或改坏被测的保证，跑覆盖这一处的测试，确认会红，再恢复（`git diff --stat` 确认和改坏前一样）。改的是门禁本身（verify 脚本、hook、CI）的，从门禁入口确认它会红。
- **按改动选测试**：项目 `AGENTS.md` 有"改了哪里跑哪些"对照表、**而且**总览清单给它配了 `trunkVerify` 的，合并前只跑按 diff 选出的测试、改坏验证和构建；全量由合并后后台的 `trunk-check.ps1` 跑（`harness.md` 第 2 节）。对照表选不出来的（改了构建、依赖、测试框架，或表里没写的目录）跑全量。没有对照表或没配 `trunkVerify` 的项目跑全量快检。
- **同一棵树只跑一次全量**：全量经 `<skill>/scripts/verify-ledger.ps1 -Command '<快检命令>'` 跑，它按代码树记账，这棵树已绿就直接打出记录。有没提交的改动时照跑、不记账。
- **慢验证按影响面选**：改动碰到了需要宿主软件、设备或 e2e 的区域，把对应的慢验证排进项目的慢验证队列（`harness.md` 第 5 节），在候选 head 上跑；没碰到的不跑。
- **判定工具先自验**：用新写的评分、比较工具判结果前，拿已知对、已知错各一例跑一遍。
- **原始输出不进仓库**：日志、导出数据、图纸副本、编译产物放 `.agents/evidence/<编号>/`（被 `.gitignore` 忽略），提交正文写路径和摘要。
- 看一眼档附截图或样例，写清看哪里、什么算对。

## 4. 定稿，交给审查

1. rebase 到最新主干，整理成要合并的提交，写好提交正文（`land.md` 第 3 节）。
2. 在这个 head 上跑第 3 节选出的测试和慢验证。
3. 按 `verify.md` 发起审查，写明 head。

定稿以后不再改提交；要改就回到第 1 步。等审查期间做不依赖它的事。

## 5. 从头重来

同一项审查连续 2 次不过：丢掉这个 worktree，带着"试过什么、为什么不行"从主干重来，或者拆小。重来仍不过，按总览第 3 节第 4 条找用户。
