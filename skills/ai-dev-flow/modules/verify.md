# 独立审查

执行方说"好了"不算数。合并前要有另一个会话的审查结论，而且对应要合并的那个 head。在主上下文里换个角色自己复查不算。

## 1. 谁来审

- **写和审不是同一个会话**。审的模型和写的同档，推理强度 `high`。按项目分工先派另一家厂商的（总览有模型设置表的用 `models.ps1 -Role review -Writer <写方模型>` 查，`orchestrate.md` 第 3 节）。
- **派不出去时**（额度、限流、未登录）：限流的过一会儿重试一次；额度用完的换同厂商的新会话，模型不低于写方那档，不为换模型降档。不因此跳过审查。
- **单向门档必须跨厂商**；换不到时告诉用户，由用户定等还是接受同厂商；接受同厂商的，强度用 `xhigh` 或 `max`。用的不是首选审查方时，记录里写明原因（第 5 节）。
- **只改文档的**（不改代码、脚本、hook、CI、配置）不请审查方：把文档里写的路径、命令、章节引用逐条实际查一遍，跑项目的文档格式检查。
- 改了门禁本身（verify 脚本、hook、CI）的，审查方要亲手改坏一处，从门禁入口确认它会红。

## 2. 审查说明

自包含，写成一个临时文件。只给目标、完成标准和 diff，不给执行方的自述或总结。审查方在一个只为它开的临时 worktree 里（检出要审的 head）工作，不改候选分支，不提交。

```
目标与完成标准：<来自队列或计划>
检出：临时 worktree <tmp>，base <sha>，head <sha>
项目规则：AGENTS.md、LESSONS.md、docs/code-standards.md（有的话）
要求：
- 只在 <tmp> 里工作；自己另开的 worktree 交回前删掉。
- 跑 <开了后台全量（对照表加 trunkVerify）的：对照表按 diff 选出的测试；否则或选不出来的：经 verify-ledger.ps1 跑全量>，写出命令、退出码、head。
- 有慢验证结果的，核对它对应的就是这个 head。
  因环境跑不了的写"没跑：<哪些>（<原因>）"。
- 改了门禁本身的：改坏一处被测代码，从门禁入口确认变红，再改回，git diff --stat 确认没差异。
- 对照目标和完成标准审，不报命名、格式、写法偏好。
- 第一轮把整份 diff 审完、问题列全；后面几轮只看修复。
- 改了功能的，看提交正文有没有对真实数据只读跑一次的结果（或"真实数据：没有，<原因>"），没有报 P1。
- 看有没有没报决定卡就做了的方向性选择（direction.md），有报 P1。
- 做法本身不成立的（实测远低于目标、多半误报），结论前单独写一行"前提不成立：<数字和依据>"。
- 只报 P0–P2，每条附可执行的证明（复现命令、会失败的测试、具体输入和输出）。
  P0、P1 另写"现实中怎么碰到"：谁、在什么正常操作下。只有特意构造的输入才触发的最多 P2。
  拿不出证明的写进"备注"。
- 没有带证明的 P0 / P1 就给 Pass。
输出：每条 ID｜P0–P2｜文件:行｜问题｜证明｜建议修法；结论 Pass 或 Fix；没覆盖到的风险。
```

高风险改动（派活和合并关口、隔离、鉴权、数据迁移、写入器）在说明里另加：想一遍中断和并发、谁会读新数据、rebase 改写提交号、一份数据多条、外部输入读不到或格式变了；完成标准附了反例清单的逐条复验（`orchestrate.md` 第 2 节）。只读工具和普通脚本不加这段，不点名让审查方找假想边界。

P0 阻止合并，P1 合并前必须修，P2 以后修：现实会碰到的排进队列（写"待放行"，`skills/next/SKILL.md` 第 3 节），构造出来的写进"没采纳"。

## 3. 发起

用 `dispatch.ps1 -Review` 派的，脚本自动开临时 worktree、审完自动删，看 `.agents/runs/<运行名>/exit.json` 的 `ReviewWorktree`：写 `kept: tracked files changed` 的是改坏检查没恢复，结论作废重来。

自己开的：在主项目工作区 `git worktree add --detach .agents/worktrees/<运行名> <head>`。审完核对候选分支 head 没变、`git -C <tmp> status --short` 没有被跟踪文件的改动（有就结论作废重来），再 `git worktree remove --force <tmp>`。

## 4. 处理结论

由你判断，不转给用户：

- 每条意见先对照代码核实，是真问题再改；没采纳的写一句理由。
- head 一变结论就作废。复审只发修复的 diff 和上一轮每条的处理结果，审查方逐条确认修好、看修复有没有带出新问题，只跑修复 diff 选出的测试，不从头审。因 rebase 带进主干改动的，也发给它看。
- 新 head 和审过的 head 之间只多了纯文档的，结论沿用，不重审。
- **第 2 轮起只认**修复带出的新问题和现实会碰到的 P0、P1；新 P2 进队列。
- **超过 2 轮先判断**：剩下的全是构造输入的，降成 P2 按 Pass 合；否则拆小重做（`build.md` 第 5 节）。第 4 轮仍不过写成 `待用户`。
- 结论里有"前提不成立"的，核实数字；成立就停下报用户（总览第 3 节第 5 条）。
- 意见不一致时以能跑出来的证明为准。

## 5. 记录

结论记在队列那一项的完成说明里：`审：<模型 强度>，<n> 轮 Pass @<head 短号>`，没采纳的意见一句带过；没用首选审查方的，写一句为什么。审查方的完整输出留在 `.agents/runs/` 或证据目录。合并前比对这个短号（`land.md` 第 1 节）。
