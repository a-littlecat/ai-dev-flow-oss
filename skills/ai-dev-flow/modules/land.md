# 合并落地

自走档按信任等级：L0 问用户，L1 摞好等用户一次合一批，L2 你直接合。看一眼档等用户说"可以"，单向门等授权。用户说过"可以合并"的直接合。合到本地主干能撤回；push、打 tag、发布是单向门，除非项目 `AGENTS.md` 写明授权。

## 1. 合并前

任何一条不满足就回到 `build.md` 或 `verify.md`，不硬合：

- 分支已定稿：rebase 到主干、提交整理好、正文写好。
- 审查结论是 Pass，没有未处理的 P0 / P1，而且**审的就是现在的 head**：`git rev-parse <分支>` 等于审查记下的 head（或只多了纯文档改动，`verify.md` 第 4 节）。只改文档的按 `verify.md` 第 1 节逐条核对过即可。
- 按改动选出的测试在这个 head 上通过过（`build.md` 第 3 节）；主干前进过、rebase 带进了别的代码的，回 `build.md` 第 4 节重新定稿。
- 按影响面选出的慢验证在这个 head 上通过（或只差纯文档）；结果没回来就保持待合并，先做别的。
- 主项目工作区没有会跟这次合并冲突的改动；`git diff --check <主干>..<分支>` 通过，diff 里只有本项的文件。

## 2. 合并

```bash
git merge --ff-only <分支>
```

项目规定用 `--no-ff` 或 PR 的按项目。

## 3. 提交正文模板

```
<区域>: <可观察的结果>（<报告人或 #编号>）

为什么：<根因或动机，一两句>
跑了：<命令 → 结果>；改坏：<撤了什么 → 哪个测试红>；真实数据：<命令和结果摘要，或"没有，<原因>">
没试：<诚实写；没有写"无">
修复：<往前修时写被修的提交 sha；否则删掉这一行>
```

"修复"一行是复盘统计返工的依据，往前修时一定写。

## 4. 合并后

- 快进合并的不在主干复跑。开了后台全量的项目，全量由 `trunk-check.ps1` 攒到机器空时跑；红了 `/next` 开场先修（往前修，原因不清或改动大的 `git revert`）。
- 队列那一项改成完成，写上审查记录（`verify.md` 第 5 节）。
- 已合并的分支和 worktree 当场删，不用问：在主项目工作区跑 `pwsh -NoProfile -File <skill>/scripts/cleanup.ps1 -Branch <分支> [-Trunk <主干>]`，审查用的临时 worktree 用 `dispatch.ps1 -CleanReviews`。脚本只删已合进主干、没有未提交改动的，不加 `--force`；它列出留着的和原因，汇报里说一句。
- push、发布，项目没授权的，在汇报"要你做"里列一行。
